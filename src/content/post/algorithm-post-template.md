# leetcode 스터디 회고글 작성 템플릿

**상태**: 초안. 기준 글은 [1주차 회고글](./blog/study-leetcode-week01.mdx)(`src/content/post/blog/study-leetcode-week01.mdx`)이며, 2주차 회고글을 쓴 뒤 구조가 더 낫다고 판단되면 이 템플릿을 2주차 버전 기준으로 교체합니다.

---

## 0. 이 템플릿의 스코프

- 매주 [DaleStudy](https://github.com/DaleStudy/leetcode-study) PR로 제출한 문제들을 정리하는 **"N주차 회고"** 글에 적용합니다.
- DP, DFS, 버킷 정렬 같은 **알고리즘 개념 자체를 깊게 설명하는 글은 이 템플릿의 대상이 아닙니다.** 개념은 별도의 "개념글"로 분리하고, 회고글에서는 링크만 겁니다 (5번 참고).
- 본문 줄바꿈(`<br />`), `<mark>` 헤딩 강조, 괄호 포함 볼드(`<strong>`) 등 전역 작성 규칙은 `blog-template.md`를 그대로 따릅니다. 여기서는 반복 설명하지 않습니다.

## 1. frontmatter

```mdx
---
title: "leetcode 스터디 N주차 회고 - [이번 주 핵심 패턴1]와 [핵심 패턴2]로 문제 풀기"
description: "[첫 문제]부터 [마지막 문제]까지, DaleStudy leetcode N주차에 푼 [개수]문제와 코드 리뷰에서 받은 피드백을 정리합니다."
date: "YYYY-MM-DD"
tags: ["알고리즘", "Hash", "DP"]
---
```

**규칙**

- `title`: `leetcode 스터디 N주차 회고 - A와 B로 문제 풀기` 패턴 고정
- `tags`: **첫 번째는 항상 `알고리즘`**. 2~3번째에 **이번 주(또는 글)의 핵심 알고리즘 개념**을 넣는다 (예: `Hash`, `DP`, `DFS`, `BFS`, `Greedy`)
  - 1주차 기준: `["알고리즘", "Hash", "DP"]`
  - 패턴이 하나면 2개도 허용: `["알고리즘", "DFS"]`
  - `LeetCode`, `스터디` 같은 메타 태그는 붙이지 않는다. 개념 태그만 쓴다

## 2. 도입부 (고정 소개문 재사용)

```mdx
[DaleStudy](https://github.com/DaleStudy/leetcode-study)는 LeetCode에서 가장 유명한 문제 모음집인 [Blind 75](https://www.teamblind.com/post/new-year-gift---curated-list-of-top-75-leetcode-questions-to-save-your-time-OaM1orEU)를 함께 풀어나가는 알고리즘 스터디입니다.<br />
매주 정해진 문제를 각자 PR로 제출하고 서로 코드 리뷰를 남기는 방식으로 진행되며, 자세한 진행 방식은 [스터디 위키](https://github.com/DaleStudy/leetcode-study/wiki)에 정리되어 있습니다.

N주차에는 아래 [개수]문제를 PR로 제출하고 리뷰를 받았습니다.

- [문제명](이슈링크)
- ...

이 글에서는 [N주차 PR](PR링크)에서 풀었던 [개수]문제를 **풀기 전에 세웠던 생각 → 실제 구현 → 리뷰어 [리뷰어명](리뷰어 GitHub 링크) 님의 피드백** 순서로 정리합니다.

---
```

**규칙**

- DaleStudy 소개 문단(1~2번째 줄)은 스터디 자체 설명이라 **매주 동일하게 재사용**한다
- "N주차에는 아래 ~문제를 PR로 제출하고 리뷰를 받았습니다" 문장에서 숫자만 갱신
- 마지막 문장의 "풀기 전 생각 → 실제 구현 → 리뷰어 피드백" 순서 선언은 고정 문구로 유지 (3번 구조와 1:1 대응)

## 3. 문제 한눈에 보기 표

```mdx
다섯 문제 모두 시간복잡도 O(n)을 달성했지만, 사용한 자료구조와 패턴은 갈렸습니다.

| 문제       | 패턴   | 복잡도(시간/공간) |
| ---------- | ------ | ------------------ |
| [문제명](이슈링크) | Hash Set | O(n) / O(n) |
```

**규칙**

- 표 위 1문장으로 이번 주 문제들의 공통점/차이점을 요약한다 (복잡도, 패턴 다양성 등)
- 컬럼은 문제 / 패턴 / 복잡도 3열 고정

## 4. 문제별 섹션 구조 (반복 단위)

문제 개수만큼 아래 3단 구조를 반복합니다.

```mdx
## 문제명 — 한줄 요약 · [#이슈번호](이슈링크)

### 풀이 전 생각

[문제를 풀기 전에 세운 접근 계획. 코드로 옮기기 전 사고 과정을 1인칭으로 서술]

## 실제 구현

실제 구현은 이렇게 됐습니다.

​```javascript
[실제 제출 코드. 로직/변수명은 원본 그대로, 주석(JSDoc 포함)은 전부 제거]
​```

[구현하면서 겪은 시행착오가 있으면 1~2문장 추가]

## 리뷰어 피드백

[리뷰 내용 요약. 원래 코드가 어땠고 리뷰어가 무엇을 지적했는지 → 어떻게 고쳤는지]

![리뷰어 [리뷰어명] 피드백 스크린샷](/images/게시글식별자/번호.png)

[리뷰를 통해 얻은 인사이트 1문장]
```

**규칙**

- 문제 제목은 `## 문제명 — 한줄 요약 · [#이슈번호](링크)` 형식 고정
- 3단 헤딩은 `### 풀이 전 생각` → `## 실제 구현` → `## 리뷰어 피드백` 레벨을 그대로 유지 (1주차 원문 기준. 통일성 있게 전부 `##`로 맞추는 안도 2주차에서 검토 가능)
- 리뷰 없이 바로 승인된 문제는 "이 문제는 리뷰어 피드백 없이 바로 승인됐습니다." 한 문장으로 짧게 처리
- 코드는 실제 제출한 원본 그대로 (로직·변수명을 설명을 위해 임의로 각색하지 않는다)
- **코드 블럭 안에는 주석을 넣지 않는다** (JSDoc `@param`/`@return`, 풀이 의도를 적은 설명 주석, 짧은 인라인 주석 전부 제거). 원본 코드에 있던 설명 주석은 삭제하지 말고 "풀이 전 생각"이나 "실제 구현" 아래 문단으로 풀어써서 살린다
- 문제 섹션 사이는 `---` 구분선

## 5. 알고리즘 개념 링크 규칙 (신규)

- 이번 주 처음 등장한 핵심 개념(버킷 정렬, DP, DFS 등)의 원리를 회고글 안에서 처음부터 설명하지 않습니다. 개념 설명은 별도 "개념글"의 역할입니다.
- "풀이 전 생각" 또는 "실제 구현" 문단에서 개념 이름이 처음 언급되는 지점에 링크를 겁니다.

**개념글이 아직 없는 경우** — 링크를 걸지 않고, 바로 위에 TODO 주석으로 자리만 남깁니다.

```mdx
<!-- TODO: 개념 정리글 작성 후 링크 연결 - 버킷 정렬(Bucket Sort) -->

정렬 없이 빈도수 자체를 인덱스로 쓰는 버킷 정렬(Bucket Sort)을 만들어서 O(n)을 달성하겠다는 계획이었습니다.
```

**개념글이 이미 있는 경우** — 개념명에 바로 인라인 링크를 겁니다.

```mdx
정렬 없이 빈도수 자체를 인덱스로 쓰는 [버킷 정렬(Bucket Sort)](/blogs/algorithm-bucket-sort)을 만들어서 O(n)을 달성하겠다는 계획이었습니다.
```

- 개념글 파일명 컨벤션(제안): `algorithm-{영문개념명-kebab}.mdx` (예: `algorithm-dynamic-programming.mdx`, `algorithm-bucket-sort.mdx`)
- 개념글 태그: `알고리즘`을 첫 번째로 두고, 두 번째에 설명하는 개념명을 넣는다 (예: `["알고리즘", "DP"]`, `["알고리즘", "버킷 정렬"]`). 파일명 `algorithm-*.mdx`로 주간 회고글(`study-leetcode-week*`)과 구분한다.
- 개념글 자체의 작성 템플릿은 이 문서의 범위 밖이며, 필요해지면 별도로 만듭니다.

**개념 진행 상황 추적표** (이 템플릿 하단에 계속 갱신)

| 개념                | 첫 등장 주차 | 개념글 상태 | 링크 |
| ------------------- | ------------ | ----------- | ---- |
| DP (Dynamic Programming) | 1주차   | 예정        | -    |
| 버킷 정렬 (Bucket Sort)   | 1주차   | 예정        | -    |

> 참고: 만약 나중에 개념을 회고글에 직접 녹이는 방식으로 정책을 바꾸게 되면, 도입부를 아래처럼 시작하는 방식으로 전환합니다.
>
> `우선 지난 주차([링크])에 가장 기초적인 DP(Dynamic Programming)의 문제 예시를 살펴보았는데요, DP가 뭔지에 대해 살펴보도록 하겠습니다.`

## 6. 마무리 섹션

```mdx
---

## 마치며

[N주차 전체 흐름을 1~2문장으로 요약]

리뷰를 받으면서 [핵심 개수]가지가 확실히 와닿았습니다.

- [인사이트 1]
- [인사이트 2]

다음 글에서는 (N+1)주차에 푼 [다음 주제] 문제들을 정리할 예정입니다.
```

**규칙**

- 1주차와 동일하게 `## 마치며` → 요약 → 인사이트 bullet → 다음 글 예고 순서 고정
- 인사이트는 "리뷰에서 배운 것" 중심 2~3개

## 7. 톤 & 체크리스트

| 항목 | 규칙 |
| --- | --- |
| 문체 | 합쇼체 (`~습니다`, `~합니다`) |
| 코드 주석 | JSDoc 스타일 `@param`/`@return` 유지 (leetcode 제출 형식 그대로) |
| 리뷰어 표기 | `[리뷰어명](GitHub 프로필 링크)` 형식으로 최초 언급 시 링크 |
| 이슈/PR 링크 | 문제 제목·표·리스트 어디서든 이슈 번호는 `#숫자` + 링크 병기 |
| 스크린샷 | 리뷰 피드백 섹션에만 사용. 리뷰 없는 문제는 스크린샷 생략 |
| 개념 설명 깊이 | 회고글 안에서는 1문장 요약 + 링크(또는 TODO)까지만. 원리 설명 금지 |
