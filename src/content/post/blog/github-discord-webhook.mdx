프론트엔드 저장소에 GitHub 알림을 Discord로 연결하는 작업을 맡으면서, 처음엔 웹훅 하나만 걸면 끝나는 줄 알았어요.<br />
그런데 PR 리뷰 알림과 CI 결과 알림을 같은 채널에 몰아넣고 나니, CI가 재실행될 때마다 메시지가 섞여서 정작 확인해야 할 리뷰 요청이 묻히는 게 눈에 보였어요.

> 사람이 만드는 협업 이벤트와, 기계가 만드는 자동 검증 결과를 같은 채널에 둬도 괜찮을까?

> GitHub 이벤트를 Discord로 보내는 방법이 여러 가지인데, 언제 Webhook을 쓰고 언제 Actions를 써야 할까?

이 글에서는 이 두 질문에 대한 답을 **채널과 Webhook을 용도별로 분리하는 방식**으로 정리한 과정을 담아요.

# 채널과 Webhook을 나눈 이유

## <mark>사람의 이벤트와 자동 결과를 분리한다</mark>

GitHub에서 Discord로 보내고 싶은 알림은 크게 두 종류였어요.<br />
하나는 PR 생성, 리뷰, 댓글, 승인, 변경 요청처럼 사람이 직접 만드는 협업 이벤트고, 다른 하나는 ESLint·타입체크·빌드·Storybook처럼 자동으로 돌아가는 CI 검증 결과예요.

이 둘을 한 채널에 두면 리뷰 알림과 CI 알림이 뒤섞이고, CI 재실행이 잦아질수록 정말 확인해야 할 메시지를 찾기 어려워져요.<br />
그래서 아래처럼 채널과 알림 경로 자체를 나눴어요.

```text
GitHub PR 이벤트
  ↓
GitHub Repository Webhook
  ↓
#프론트-github-webhook
  ↓
PR 생성 / 리뷰 / 댓글 / 승인 / 변경 요청 알림

GitHub Actions CI 완료
  ↓
PR Discord Notification workflow
  ↓
#프론트-github-ci-bot
  ↓
CI 성공 / CI 실패 알림
```

| Discord 채널               | 역할                        | 메시지를 보내는 주체       |
| --------------------------- | --------------------------- | -------------------------- |
| `#프론트-github-webhook`   | PR·리뷰·댓글 등 협업 활동 알림 | GitHub Repository Webhook |
| `#프론트-github-ci-bot`    | CI 성공·실패 알림           | GitHub Actions             |

GitHub Webhook은 GitHub에서 특정 이벤트가 발생했을 때 지정한 URL로 HTTP 요청을 직접 보내는 기능이고, Discord Incoming Webhook은 특정 채널에 메시지를 남길 수 있는 전용 URL이에요.

<LinkCard url="https://docs.github.com/en/webhooks/about-webhooks" />

채널이 2개면 이 둘을 연결하는 Webhook도 2개가 필요해요.<br />
이후 섹션에서 각각을 어떻게 구성했는지 정리해요.

# GitHub Webhook으로 협업 이벤트 받기

### 실제로 받는 이벤트

첫 번째 채널 `#프론트-github-webhook`에는 아래 이벤트만 들어와요.

- PR 생성
- PR 리뷰 요청
- PR 승인 / 변경 요청
- PR 코드 리뷰 댓글
- PR 리뷰 스레드 해결
- PR 일반 댓글
- PR 병합 또는 닫힘

<br />

## <mark>이벤트는 최소한으로 고른다</mark>

GitHub Repository Webhook 설정 화면에서 이벤트를 고를 때, 실제로 체크한 것과 체크하지 않은 것을 나눠보면 이래요.

| GitHub Event                  | 실제 동작                        | Discord 알림 여부       |
| ------------------------------ | --------------------------------- | ------------------------- |
| Pull requests                  | PR 생성, 닫힘, 병합, 리뷰어 요청 등 | 전송                     |
| Pull request reviews           | Approve, Request changes 등 리뷰 제출 | 전송                 |
| Pull request review comments   | 코드 줄 단위 inline 댓글           | 전송                     |
| Pull request review threads    | 리뷰 스레드 resolve/unresolve      | 전송                     |
| Issue comments                 | PR 일반 댓글, Issue 댓글           | 전송                     |
| Pushes                         | 브랜치에 커밋 push                 | 미전송                   |
| Workflow runs / Check runs     | CI workflow·check 상태             | 미전송 (Actions가 담당) |

<LinkCard url="https://docs.github.com/en/webhooks/webhook-events-and-payloads" />

여기서 `Pushes`를 체크하지 않은 게 중요해요.<br />
PR 브랜치에 커밋을 push할 때마다 알림이 오면 채널이 금방 시끄러워지기 때문에, 실제로 팀원이 확인해야 하는 이벤트(PR 생성·리뷰·승인·변경 요청·댓글)만 받도록 걸러냈어요.

<br />

### Payload URL 끝에 /github를 붙이는 이유

GitHub Repository Webhook의 Payload URL은 일반 Discord Webhook URL과 조금 다르게 설정해요.

```text
https://discord.com/api/webhooks/{WEBHOOK_ID}/{WEBHOOK_TOKEN}/github
```

GitHub와 Discord는 기본 Webhook payload 형식이 달라요.<br />
GitHub는 GitHub 이벤트 JSON을 그대로 보내는데, Discord의 일반 Incoming Webhook은 Discord 메시지 JSON을 기대해요.

그래서 URL 끝에 `/github`를 붙여야, Discord가 GitHub payload를 해석해서 사람이 읽을 수 있는 메시지로 변환해줘요.

<LinkCard url="https://discord.com/developers/docs/resources/webhook" />

<br />

### ping 테스트로 연결부터 확인한다

GitHub Repository Webhook을 저장하면 GitHub가 자동으로 `ping` 이벤트를 보내요.<br />
여기서 확인한 응답은 아래와 같았어요.

```text
Event: ping
Response: 204
Completed in: 0.08 seconds
```

HTTP 204는 요청이 정상 처리됐지만 별도 응답 본문은 없다는 뜻이라, 이 시점에는 연결 자체만 확인된 상태예요.<br />
GitHub 저장소의 Settings → Webhooks → 해당 Webhook → Recent deliveries에서 전송 기록을 볼 수 있고, 원하면 Redeliver로 다시 보낼 수도 있어요.

실제 협업 알림은 PR을 만들어야 확인할 수 있어서, 빈 커밋으로 테스트 PR을 하나 열어봤어요.

```bash
git checkout -b chore/test-github-webhook
git commit --allow-empty -m "chore: test github webhook"
git push -u origin chore/test-github-webhook
```

이 브랜치로 `develop`을 대상으로 PR을 생성하면 `Pull requests → opened` 이벤트가 발생하고, `#프론트-github-webhook`에 메시지가 와야 정상이에요.<br />
반대로 로컬에서 파일만 수정하거나 단순히 `git push`만 하는 것으로는 알림이 오지 않는데, `Pushes` 이벤트를 체크하지 않았기 때문이에요.<br />
GitHub 입장에서는 PR이 열려야 비로소 `pull_request` 이벤트가 발생해요.

# GitHub Actions로 CI 결과만 골라 보내기

## <mark>Workflow 전체가 끝났을 때만 보낸다</mark>

GitHub Repository Webhook에서 `Check runs`, `Workflow jobs`, `Workflow runs` 같은 이벤트도 고를 수 있긴 해요.<br />
그런데 이렇게 하면 CI 내부 job마다 알림이 따로 오게 돼요.

```text
ESLint 완료 → 알림
Type check 완료 → 알림
Build 완료 → 알림
Storybook build 완료 → 알림
Storybook test 완료 → 알림
```

메시지가 너무 많아지고, "전체 CI가 정말 성공했는지"를 한 번에 판단하기도 어려워요.<br />
그래서 `ci`와 `storybook` job이 모두 끝나 전체 workflow의 conclusion이 결정된 시점에만, 별도 workflow가 Discord로 메시지 1개를 보내도록 나눴어요.

```text
ci job 완료
storybook job 완료
  ↓
CI workflow 전체 conclusion 결정
  ↓
PR Discord Notification 실행
  ↓
Discord 메시지 1개 전송
```

<br />

### ci.yml: 언제, 무엇을 검사하는가

CI workflow는 핵심 브랜치인 `develop`, `main`에 대해서만 돌게 했어요.

```yaml
name: CI

on:
  push:
    branches: [develop, main]
  pull_request:
    branches: [develop, main]

permissions:
  contents: read
```

`permissions: contents: read`는 CI가 코드만 checkout해서 검사하면 되므로, 읽기 권한만 부여한 거예요.<br />
PR 수정이나 Secret 변경, repository push는 할 수 없어요.

같은 PR에 새 커밋이 push되면 이전 CI를 취소하도록 concurrency도 걸었어요.

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

`cancel-in-progress`를 `pull_request` 이벤트일 때만 `true`로 둬서, PR 브랜치의 오래된 커밋에 대한 CI는 취소하되 `main`·`develop`에 직접 push한 CI는 취소하지 않도록 했어요.

이 workflow는 두 job으로 나뉘어요.<br />
하나는 코드 품질과 빌드를 검사하는 `ci` job이고,

```yaml
- uses: actions/checkout@v4
  with:
    persist-credentials: false

- uses: actions/setup-node@v4
  with:
    node-version-file: .nvmrc
    cache: npm

- id: install
  run: npm ci
```

다른 하나는 Storybook을 빌드하고 interaction·접근성 테스트를 돌리는 `storybook` job이에요.

```yaml
- name: Install Playwright (chromium)
  run: npx playwright install --with-deps chromium

- name: Build Storybook
  run: npm run build-storybook

- name: Test Storybook
  run: npm run test-storybook
```

`npm ci`는 `package-lock.json`과 정확히 일치하는 의존성만 설치해서, `npm install`과 달리 lockfile을 임의로 바꾸지 않아요.<br />
CI에는 이 재현성이 더 중요해서 `npm ci`를 썼어요.<br />
`persist-credentials: false`는 checkout 이후 GitHub 인증 토큰이 git remote URL에 남지 않도록 하는 보안 설정이에요.

지금은 두 job 사이에 `needs`를 걸지 않아서 병렬로 실행돼요.<br />
실패 항목을 한 번에 모두 확인하고 싶어서 내린 선택인데, `# needs: ci` 주석을 풀면 `ci`가 실패했을 때 Storybook job(특히 Playwright 설치 시간)을 건너뛸 수 있어요.<br />
다만 전체 CI 시간은 길어져요.

이전에 실측해본 경험상, Storybook의 play 기반 interaction test는 모달 포커스 트랩, Esc 키 처리, 로딩 중 접근 가능한 이름 유지처럼 정적 lint나 axe만으로는 놓치기 쉬운 결함을 잡아낼 때가 많았어요.

<br />

### PR과 연결하고, draft·closed는 거른다

CI 알림 workflow는 `workflow_run` 이벤트로 트리거돼요.

```yaml
name: PR Discord Notification

on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
```

여기서 `workflows: ["CI"]`의 `"CI"`는 `ci.yml`의 `name: CI`와 **정확히 일치**해야 해요.<br />
이름이 다르면 아예 감지되지 않아요.

```yaml
# ci.yml
name: Frontend CI

# discord-pr-notification.yml
workflows: ["CI"]
```

위 예시처럼 `Frontend CI`와 `CI`는 다른 workflow 이름이라 연결되지 않아요.

<LinkCard url="https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#workflow_run" />

알림은 PR에서 실행된 CI가 성공하거나 실패했을 때만 보내요.

```yaml
if: >-
  github.event.workflow_run.event == 'pull_request' &&
  (github.event.workflow_run.conclusion == 'success' ||
   github.event.workflow_run.conclusion == 'failure')
```

`develop`·`main`에 직접 push한 CI, 취소되거나 skipped된 CI는 여기서 걸러져요.<br />
같은 커밋 SHA에서 알림 workflow가 여러 번 실행되는 경우를 대비해 concurrency도 걸었어요.

```yaml
concurrency:
  group: discord-${{ github.event.workflow_run.head_sha }}
  cancel-in-progress: true
```

PR 정보는 `workflow_run` payload에서 먼저 찾고, 없으면 커밋 SHA로 다시 검색해요.

```js
const run = context.payload.workflow_run;
let ref = (run.pull_requests || [])[0];

if (!ref) {
  const { data } = await github.rest.repos.listPullRequestsAssociatedWithCommit({
    owner,
    repo,
    commit_sha: run.head_sha,
  });

  ref = data.find((pr) => pr.state === "open");
}

const { data: pr } = await github.rest.pulls.get({ owner, repo, pull_number: ref.number });
```

`workflow_run.pull_requests`가 fork PR 등 일부 상황에서 비어 있을 수 있어서, 커밋 SHA와 연결된 열린 PR을 GitHub API로 다시 찾는 fallback을 넣었어요.

닫혔거나 draft인 PR은 알림을 보내지 않도록 걸렀어요.

```js
if (pr.state !== "open" || pr.draft) {
  core.info("닫힘/draft PR → 스킵");
  return;
}
```

Draft PR은 아직 리뷰 요청 전인 작업 중 상태라, "CI 통과 — 리뷰 부탁드립니다" 같은 메시지를 보내면 맥락에 안 맞기 때문이에요.

### 성공/실패 메시지와 멘션

CI 결과에 따라 아래 형식으로 메시지를 만들어요.

```text
✅ CI 통과 — 리뷰 부탁드립니다
📌 PR 제목
🔗 PR 링크
👤 작성자 @DiscordUser
👁️ 리뷰어 @DiscordReviewer
```

```text
❌ CI 실패 — 확인 필요
📌 PR 제목
🔗 PR 링크
👤 작성자 @DiscordUser
🪵 로그 CI 실행 링크
```

실패 메시지의 로그 링크는 `run.html_url`을 그대로 써서, 클릭하면 실패한 GitHub Actions 실행 페이지로 바로 이동해요.

### Webhook URL과 사용자 ID는 반드시 가려서 관리한다

CI Bot은 Discord에 직접 HTTP 요청을 보내요.

```js
await fetch(process.env.DISCORD_WEBHOOK, {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ content }),
});
```

```yaml
env:
  DISCORD_WEBHOOK: ${{ secrets.DISCORD_WEBHOOK_URL }}
```

Discord Webhook URL을 아는 사람은 봇 계정 로그인 없이도 그 채널에 메시지를 보낼 수 있어서, 사실상 채널 전송 권한을 가진 비밀 키예요.<br />
그래서 코드나 README, PR 본문, 스크린샷 어디에도 URL 전체가 그대로 보이면 안 되고, GitHub Repository Secret에만 저장해야 해요.<br />
이 Secret에는 앞서 나온 `/github`를 붙이지 않는데, Discord 형식 JSON을 Actions 코드가 직접 만들어서 보내기 때문이에요.

성공 메시지에 작성자·리뷰어를 실제 멘션으로 표시하려고 GitHub 아이디와 Discord 사용자 ID를 매핑하는 Repository Variable도 하나 더 뒀어요.<br />
아래는 예시 형태예요.

```json
{ "octocat": "111111111111111111", "hubot": "222222222222222222" }
```

```js
const m = (login) => (map[login] ? `<@${map[login]}>` : `\`${login}\``);
```

```js
allowed_mentions: {
  parse: ["users"];
}
```

`allowed_mentions.parse`에 `"users"`를 넣어야 메시지 안의 `<@디스코드ID>` 형식을 Discord가 실제 멘션으로 해석해요.<br />
매핑이 없는 GitHub 아이디는 그냥 `octocat`처럼 코드 텍스트로만 표시돼요.<br />
이 값은 Discord Webhook URL과 달리 채널 전송 권한을 직접 가진 값은 아니라서, Secret 대신 Repository Variable로 관리했어요.

<LinkCard url="https://docs.github.com/en/actions/learn-github-actions/variables" />

두 Webhook을 정리하면 이래요.

| 구분                 | PR 협업 Webhook               | CI Bot Webhook                |
| -------------------- | ------------------------------ | ------------------------------ |
| Discord 채널         | `#프론트-github-webhook`      | `#프론트-github-ci-bot`       |
| 호출 주체            | GitHub Repository Webhook      | GitHub Actions                 |
| URL 형식             | `.../webhooks/.../github`      | `.../webhooks/...`             |
| `/github` 필요 여부  | 필요                            | 필요 없음                      |
| 메시지 형식          | Discord가 GitHub payload 변환  | workflow 코드가 직접 생성      |

## 실제 PR로 검증하기

두 workflow 파일은 로컬에만 있으면 GitHub가 존재를 몰라요.<br />
그래서 먼저 설정 커밋을 만들어 기본 브랜치에 올리는 게 순서예요.

```bash
git add .github/workflows/ci.yml
git add .github/workflows/discord-pr-notification.yml
git commit -m "ci: add CI and Discord notifications"
git push -u origin chore/add-ci-discord-notifications
```

이 PR에서는 GitHub Webhook PR 알림과 CI 실행까지는 확인할 수 있어요.<br />
다만 CI가 끝났을 때 `PR Discord Notification`이 안정적으로 실행되려면, `workflow_run`이 다른 workflow의 완료를 감지하는 후속 트리거라는 특성상 알림 workflow 파일이 **기본 브랜치**에 있어야 해요.<br />
그래서 설정 PR을 먼저 병합한 뒤, 별도의 테스트 PR로 두 번째 검증을 하는 편이 가장 확실해요.

성공 흐름을 확인한 다음에는 일부러 실패도 만들어봐야, 실패 메시지와 로그 링크가 정상인지까지 확인할 수 있어요.<br />
`typecheck` 스크립트를 잠깐 `exit 1`로 바꿔 push하고, 확인 후 되돌리는 방식으로 테스트했어요.

## 마치며

PR·리뷰 같은 협업 이벤트는 GitHub Repository Webhook이 직접 처리하고, CI 성공·실패는 GitHub Actions가 전체 workflow가 끝난 시점에만 판단해서 보내도록 나눴어요.

- Webhook과 Actions는 이벤트를 받는 방식 자체가 달라서, `/github` suffix 하나로도 payload 형식 차이가 확연히 체감됐어요.
- job 단위로 알림을 보내는 대신 workflow 전체 conclusion이 결정된 시점에만 메시지 1개를 보내는 편이 신호 대비 잡음이 훨씬 적었어요.
- Webhook URL과 Discord 사용자 ID처럼 채널 접근 권한과 연결되는 값은 Secret과 더미 매핑으로 분리해서 다뤄야 한다는 걸 다시 확인했어요.

다음 글에서는 설정 PR을 실제로 병합한 뒤 두 채널에서 확인한 결과와, 검증 과정에서 만난 트러블슈팅을 정리할 예정이에요.
