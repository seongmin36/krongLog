## Express 미들웨어 파이프라인

### 서버 내부의 전체 흐름

브라우저에서 `GET /users/1`을 보내면 서버 안에서는 다음 흐름이 일어난다.

```bash
포트 오픈 : Node.js HTTP Server > listen()
   ↓
요청 수신 : TCP connection
   ↓
HTTP 파싱 : Node.js HTTP parser
   ↓
Express 전달 : Express 서버 내부 동작 방식
   ↓
응답 생성 및 전송
   ↓
커넥션 종료/유지 : Keep-Alive
```

이 흐름은 크게 **Node 레벨**과 **Express 레벨** 두 층으로 나뉜다.

| 레벨 | 역할 |
|------|------|
| Node 레벨 | TCP 연결 수신, HTTP 요청 파싱, req/res 객체 생성 |
| Express 레벨 | 등록된 미들웨어/라우터를 **순서대로** 탐색 후 핸들러 실행 |

> **핵심**: Express는 우선순위 엔진이 아니라 **순차 탐색 구조**다.  
> 미들웨어 등록 순서가 곧 실행 순서다.

### 미들웨어 체인(Middleware Chain)

`req → middleware1 → middleware2 → ... → res` 순으로 이어지는 구조다.

```bash
클라이언트          :  GET /users/1 HTTP/1.1
                        Host: localhost:3000
                        Authorization: Bearer xxx
   ↓
Node HTTP 서버      : 요청 수신
   ↓
req/res 객체 생성
   ↓
Express app에 전달  : 등록된 미들웨어와 라우터 탐색
   ↓
미들웨어 체인 실행  : 순차적으로 실행, next()로 넘어감
   ↓
라우터 매칭         : GET /users/1 → userRouter 진입
   ↓
핸들러 실행         : DB 조회, 검증, 인증, 응답 데이터 조립
   ↓
응답 반환           : 상태코드 + 헤더 + JSON 직렬화 + 바디 전송
   ↓
응답 종료 후 후처리 : res.on('finish') → 로깅, 상태코드 기록
```

실제 인증 API의 미들웨어 구성 예시는 다음과 같다.

```bash
Request
   ↓
requestId middleware   : 요청 추적용 ID 부여
   ↓
logger middleware      : 접근 로그 기록
   ↓
json parser            : req.body 파싱
   ↓
auth middleware        : 로그인 사용자 확인
   ↓
zod validation         : 요청 스키마 검증
   ↓
router                 : 경로 분기
   ↓
controller             : 요청/응답 책임
   ↓
service                : 비즈니스 로직
   ↓
prisma                 : DB 접근
   ↓
response
```

### `next()` 함수의 역할

Express의 요청 흐름은 결국 아래 세 가지 중 하나로 끝난다.

| 분기 | 코드 | 의미 |
|------|------|------|
| 정상적으로 다음으로 넘김 | `next()` | 다음 미들웨어로 제어권 이동 |
| 여기서 응답하고 종료 | `res.json(...)` | 응답 후 체인 종료 |
| 에러로 넘김 | `next(err)` / `throw err` | 에러 미들웨어로 점프 |

### 에러 미들웨어: 왜 인자가 반드시 4개여야 하는가?

Express는 **인자 개수**로 일반 미들웨어와 에러 처리용 미들웨어를 구분한다.
`(err, req, res, next)` 형태의 함수만 에러 핸들러로 인식한다.

```typescript
// ✅ 올바른 에러 미들웨어 (인자 4개)
import { Request, Response, NextFunction } from "express";

export const errorMiddleware = (
  err: Error,
  _req: Request,
  res: Response,
  _next: NextFunction,
) => {
  console.error(`[Error Middleware] ${err.message}`);

  const message = err instanceof Error ? err.message : "Internal Server Error";

  res.status(500).json({
    ok: false,
    message,
  });
};
```

#### 실험: 인자를 3개로 줄이면 어떻게 되는가?

```typescript
// ❌ 잘못된 에러 미들웨어 (인자 3개 — Express가 에러 핸들러로 인식 못 함)
export const errorMiddleware = (
  err: Error,
  _req: Request,
  res: Response,
  // _next: NextFunction, ← 주석 처리
) => {
  res.status(500).json({ ok: false, message: err.message });
};
```

**결과**: 커스텀 에러 미들웨어가 건너뛰어지고 Express 기본 에러 핸들러가 동작해 `HTML` 형식의 스택 트레이스 페이지가 반환된다.

흐름을 정리하면:

```bash
next(err) 발생
   ↓
커스텀 에러 미들웨어 건너뜀 (인자 4개가 아니므로)
   ↓
Express 기본 에러 핸들러가 잡음
   ↓
HTML 스택 트레이스 응답
```

#### 실험: `next()` 없이 핸들러를 종료하면 어떻게 되는가?

```typescript
// ⚠️ next()도 res.send()도 없는 핸들러
router.get("/hang-test", (_req, _res, _next) => {
  console.log("여기까진 옴");
  // 응답도, 다음 미들웨어 호출도 없음
});
```

**결과**: 클라이언트는 약 30초 후 타임아웃이 걸려 무한 로딩 상태가 된다.  
`next()`나 `res.*()` 중 하나는 반드시 호출해야 체인이 이어진다.

## Node.js 이벤트 루프와 싱글 스레드 모델

### 왜 싱글 스레드인데 동시 처리가 가능한가?

Node.js의 **JavaScript 실행 메인 스레드는 하나**다.  
그러나 I/O가 발생하면 직접 기다리지 않고 **시스템 커널 또는 libuv**에 위임한다.

| 구성 요소 | 역할 |
|-----------|------|
| **OS 커널** | 네트워크 소켓, HTTP 요청 수신, DB TCP 연결 등 시스템 자원 관리 |
| **libuv** | 이벤트 루프 관리, 비동기 I/O 추상화, OS별 차이 흡수, 스레드풀 제공 |

> libuv가 있기 때문에 동일한 JavaScript 코드가 Linux / macOS / Windows에서 유사하게 동작한다.

각 OS가 제공하는 비동기 I/O 방식은 서로 다르다.

| OS | 비동기 I/O 방식 |
|----|----------------|
| Linux | `epoll` |
| macOS | `kqueue` |
| Windows | `IOCP` |

libuv는 이 차이를 추상화하는 **C 라이브러리**다.

### 파일 읽기 요청의 실제 흐름

```typescript
import { readFile } from "node:fs/promises";

app.get("/file", async (_req, res) => {
  const content = await readFile("./a.txt", "utf-8");
  res.send(content);
});
```

```bash
클라이언트 요청
   ↓
Node HTTP Server 수신
   ↓
Express 라우트 실행
   ↓
readFile() 호출
   ↓
libuv 스레드풀에 작업 위임       ← JS 메인 스레드는 여기서 놓아줌
   ↓
그동안 Node는 다른 요청 처리 가능
   ↓
파일 읽기 완료 (libuv 스레드풀)
   ↓
이벤트 루프가 Promise 후속 실행
   ↓
res.send()
```

> 네트워크 I/O는 OS 커널이, 파일 I/O는 libuv 스레드풀이 처리한다.  
> "메인 JS가 while문 돌면서 기다리는 게 아님"이 핵심이다.

### 역할 비유

| 비유 | 실제 구성 요소 |
|------|---------------|
| 사장 (회계 담당) | Node.js 메인 스레드 |
| 매니저 (지휘·조율) | 이벤트 루프 |
| 전문 요리사 (주문 처리) | libuv / OS 커널 |
| 홀 서빙 알바 1명 | 싱글 스레드 |

요리사가 일을 마치면 알바에게 전해주고, 매니저(이벤트 루프)가 다음 실행을 지시한다.

## 이벤트 루프 동작 순서 실험

### 실험 1: 동기 / Promise / Timer 실행 순서

```typescript
console.log("1. start");

setTimeout(() => {
  console.log("2. setTimeout");
}, 0);

Promise.resolve().then(() => {
  console.log("3. promise then");
});

console.log("4. end");
```

**결과**: `1. start` → `4. end` → `3. promise then` → `2. setTimeout`

| 큐 종류 | 포함 항목 | 실행 우선순위 |
|---------|-----------|--------------|
| 동기 코드 | `console.log` | 1순위 |
| 마이크로태스크 큐 | `Promise.then` | 2순위 |
| 매크로태스크 큐 (타이머) | `setTimeout` | 3순위 |

### 실험 2: `setTimeout(0)` vs `setImmediate()`

```typescript
console.log("start");

setTimeout(() => {
  console.log("setTimeout 0");
}, 0);

setImmediate(() => {
  console.log("setImmediate");
});

console.log("end");
```

**결과**: 메인 컨텍스트에서는 `setTimeout`과 `setImmediate`의 순서가 **비결정적**으로 나타날 수 있다.  
`setTimeout(0)`은 "즉시"가 아니라 타이머 만료 후 큐에 들어간다.

### 실험 3: I/O 콜백 내부에서의 순서

```typescript
import fs from "node:fs";

fs.readFile(import.meta.url, () => {
  console.log("I/O callback");

  setTimeout(() => {
    console.log("setTimeout inside I/O");
  }, 0);

  setImmediate(() => {
    console.log("setImmediate inside I/O");
  });
});
```

**결과**: I/O 콜백 내부에서는 `setImmediate`가 `setTimeout`보다 먼저 실행된다.

> I/O 콜백이 처리되는 단계(poll phase) 직후가 `check phase`(setImmediate 실행 단계)이기 때문이다.

### 실험 4: `process.nextTick()` 우선순위

```typescript
// node src/playground/event-loop.cjs 로 실행 (순수 Node.js 환경)
console.log("start");

setTimeout(() => console.log("setTimeout"), 0);
setImmediate(() => console.log("setImmediate"));
Promise.resolve().then(() => console.log("promise then"));
process.nextTick(() => console.log("nextTick"));

console.log("end");
```

**결과 (순수 Node.js CJS 환경)**: `start` → `end` → `nextTick` → `promise then` → `setTimeout` / `setImmediate`

#### 주의: 실행 환경에 따라 결과가 달라진다

`tsx`로 실행하면 `promise then`이 `nextTick`보다 먼저 출력되는 현상이 발생한다.

**원인**:
- ESM 모듈 시스템은 파일의 첫 줄이 실행되기 전부터 이미 `Promise` 환경(마이크로태스크 큐) 안에서 동작한다.
- `tsx`는 코드를 변환하면서 **비동기 래퍼(Async Wrapper)**로 감싸 실행하므로, 그 내부에서 `Promise.then`이 `process.nextTick`보다 우선권을 가질 수 있다.

> **결론**: `process.nextTick`의 우선순위는 이론상 Promise보다 높지만,  
> **실행 환경(ESM vs CJS), 실행 도구(tsx, babel-node), Node.js 버전**에 따라 순서가 달라질 수 있다.  
> 실제 동작은 반드시 **순수 Node.js 환경**에서 검증하라.

CJS와 ESM의 차이에 대해서는 [CJS vs ESM](#) 페이지에서 더 자세히 다룬다.

## 정리

| 개념 | 핵심 요약 |
|------|-----------|
| Express 미들웨어 체인 | 등록 순서대로 순차 실행, `next()`로 이어붙임 |
| 에러 미들웨어 | 인자 4개 `(err, req, res, next)` 필수 — Express가 형태로 구분 |
| `next()` 없는 핸들러 | 응답 없이 연결이 끊기지 않아 클라이언트 무한 로딩 |
| Node.js 싱글 스레드 | JS 실행은 1개 스레드이지만 I/O는 OS 커널 / libuv에 위임 |
| 이벤트 루프 큐 순서 | 동기 → `process.nextTick` → `Promise.then` → `setTimeout` / `setImmediate` |
| `setImmediate` vs `setTimeout` | I/O 내부에서는 `setImmediate`가 더 빠름, 외부에서는 비결정적 |

HTTP 메서드와 상태 코드, Header & Body에 대한 내용은 별도 게시글에서 다룰 예정이다.
