Node.js로 백엔드를 시작하면서 가장 먼저 부딪힌 두 가지 질문이 있었다.

> "미들웨어가 어떤 순서로 실행되는 거지?"

이 글에서는 Express 미들웨어 파이프라인의 동작 구조와 Node.js 이벤트 루프의 실행 순서를 **직접 실험한 결과**를 바탕으로 정리한다.

## Express 미들웨어 파이프라인

### 요청이 서버에 도착하면 무슨 일이 벌어지는가?

브라우저에서 `GET /users/1`을 보냈다고 가정하자. 이 요청은 Node.js HTTP 서버가 TCP 연결을 수신하고, HTTP를 파싱한 뒤, `req`/`res` 객체를 만들어 Express에 넘기는 과정을 거친다.

여기서 중요한 건 Express가 **우선순위 엔진이 아니라 순차 탐색 구조**라는 점이다. 등록된 미들웨어를 위에서 아래로 순서대로 실행하고, `next()`를 호출하면 다음 미들웨어로 넘어간다.

### 미들웨어 체인의 동작 방식

Express의 요청 처리 흐름은 이렇게 생겼다.

```text
Client Request → Global Middleware → Router → Route Middleware → Controller → Response
```

이걸 `next()`로 이어붙이는 구조를 **Middleware Chain**이라 한다.

실제 인증 API를 기준으로 미들웨어가 어떻게 쌓이는지 보면 직관적이다.

```text
Request
  ↓
requestId    →  요청 추적용 ID 부여
  ↓
logger       →  접근 로그 기록
  ↓
json parser  →  req.body 파싱
  ↓
auth         →  로그인 사용자 확인
  ↓
validation   →  요청 스키마 검증 (Zod)
  ↓
router       →  경로 분기
  ↓
controller   →  요청/응답 책임
  ↓
service      →  비즈니스 로직
  ↓
prisma       →  DB 접근
  ↓
Response
```

각 단계가 `next()`를 호출해야 다음으로 넘어간다. 호출하지 않으면? 요청은 거기서 멈춘다.

### 흐름을 결정하는 세 가지 분기

Express의 요청 흐름은 결국 아래 세 가지 중 하나로 끝난다.

| 분기 | 코드 | 의미 |
|------|------|------|
| 다음으로 넘김 | `next()` | 다음 미들웨어로 제어권 이동 |
| 여기서 응답 | `res.json(...)` | 응답 후 체인 종료 |
| 에러로 점프 | `next(err)` / `throw` | 에러 미들웨어로 이동 |

에러가 발생하면 일반 미들웨어를 전부 건너뛰고 에러 미들웨어로 직행한다.

```
middleware → 문제 발생 → next(err) → error middleware → error response
```

### 라우터 매칭 구조

`/users/1` 요청이 들어오면 Express는 이런 순서로 매칭한다.

1. app 레벨에서 `/users` prefix를 찾아 `userRouter`로 진입
2. router 내부에서 `/:id`에 해당하는 route 탐색
3. 매칭된 handler 실행

```typescript
router.get('/:id', authMiddleware, userController.getUserById);
```

여기서 `authMiddleware`는 **라우트 미들웨어**로, 이 특정 경로에서만 실행된다. 글로벌 미들웨어와 달리 필요한 라우트에만 붙일 수 있다.

## 에러 미들웨어는 왜 인자가 4개여야 할까?

Express 에러 미들웨어를 처음 접했을 때 가장 의아했던 건 **인자가 반드시 4개**여야 한다는 규칙이었다. 궁금해서 직접 실험해봤다.

### 올바른 에러 미들웨어

```typescript
import { Request, Response, NextFunction } from "express";

export const errorMiddleware = (
  err: Error,
  _req: Request,
  res: Response,
  _next: NextFunction,
) => {
  console.error(`[Error] ${err.message}`);
  res.status(500).json({
    ok: false,
    message: err.message,
  });
};
```

이건 정상 동작한다. `(err, req, res, next)` — 4개의 인자를 받고 있기 때문이다.

### 실험: 인자를 3개로 줄이면?

```typescript
// next 파라미터를 제거한 에러 미들웨어
export const errorMiddleware = (
  err: Error,
  _req: Request,
  res: Response,
) => {
  res.status(500).json({ ok: false, message: err.message });
};
```

Express는 함수의 `.length` 프로퍼티(인자 개수)로 일반 미들웨어와 에러 미들웨어를 구분한다. 인자가 3개면 일반 미들웨어로 취급해서, `next(err)` 호출 시 이 함수를 **건너뛴다**. 결과적으로 Express 기본 에러 핸들러가 동작하면서 HTML 스택 트레이스 페이지가 반환된다.

> [Express 소스 코드](https://github.com/expressjs/express/blob/main/lib/router/index.js#L586)를 보면 `fn.length === 4`일 때만 에러 핸들러로 인식하는 분기가 있다. 단순하지만, 모르면 디버깅에 시간을 많이 쓰게 되는 부분이다.

### 실험: next()도 res도 호출하지 않으면?

```typescript
router.get("/hang-test", (_req, _res, _next) => {
  console.log("여기까진 옴");
  // 응답도, 다음 미들웨어 호출도 없음
});
```

이 경우 클라이언트는 약 30초 후 타임아웃이 걸려 **무한 로딩** 상태가 된다. `next()`나 `res.*()` 중 하나는 반드시 호출해야 요청-응답 사이클이 완결된다.

## Node.js 이벤트 루프: 싱글 스레드의 비밀

### 왜 싱글 스레드인데 동시 처리가 되는가

Node.js의 JavaScript 실행 스레드는 **딱 하나**다. 한 순간에 JS 코드는 하나의 작업만 실행한다.

그런데 I/O가 발생하면 이야기가 달라진다. 파일 읽기, 네트워크 요청 같은 작업을 직접 기다리지 않고 **시스템 커널 또는 libuv**에 위임한다. 작업이 끝나면 콜백이 이벤트 루프를 통해 실행 큐에 올라온다.

| 구성 요소 | 역할 |
|-----------|------|
| **OS 커널** | 네트워크 소켓, TCP 연결, DB 커넥션 등 시스템 자원 관리 |
| **libuv** | 이벤트 루프 관리, 비동기 I/O 추상화, 스레드풀 제공 |

각 OS마다 비동기 I/O 방식이 다르다(Linux는 `epoll`, macOS는 `kqueue`, Windows는 `IOCP`). libuv가 이 차이를 추상화해주기 때문에, 같은 JavaScript 코드가 어느 OS에서든 동일하게 동작한다.

### 파일 I/O의 실제 흐름

```typescript
import { readFile } from "node:fs/promises";

app.get("/file", async (_req, res) => {
  const content = await readFile("./data.txt", "utf-8");
  res.send(content);
});
```

`readFile()`이 호출되면 JS 메인 스레드는 파일 읽기를 **libuv 스레드풀에 위임**하고, 즉시 다른 요청을 처리하러 간다. 파일 읽기가 끝나면 이벤트 루프가 Promise 후속 처리를 실행하고, 그때 `res.send()`가 호출된다.

네트워크 I/O는 OS 커널이, 파일 I/O는 libuv 스레드풀이 처리한다. 메인 JS 스레드가 while문 돌면서 기다리는 게 아니라는 점이 핵심이다.

## 이벤트 루프 실행 순서 실험

이론만으로는 확신이 안 생겨서 직접 코드를 짜고 실행해봤다.

### 실험 1: 동기 / Promise / Timer

```javascript
console.log("1. start");

setTimeout(() => {
  console.log("2. setTimeout");
}, 0);

Promise.resolve().then(() => {
  console.log("3. promise then");
});

console.log("4. end");
```

**결과**: `1. start` → `4. end` → `3. promise then` → `2. setTimeout`

동기 코드가 먼저, 마이크로태스크(Promise)가 그다음, 매크로태스크(setTimeout)가 마지막이다. `setTimeout(0)`이라고 "즉시" 실행되는 게 아니다.

### 실험 2: setTimeout(0) vs setImmediate()

```javascript
setTimeout(() => console.log("setTimeout"), 0);
setImmediate(() => console.log("setImmediate"));
```

메인 컨텍스트에서 실행하면 두 함수의 순서가 **비결정적**이다. 실행할 때마다 바뀔 수 있다.

하지만 **I/O 콜백 내부**에서는 이야기가 다르다.

```javascript
import fs from "node:fs";

fs.readFile(import.meta.url, () => {
  setTimeout(() => console.log("setTimeout inside I/O"), 0);
  setImmediate(() => console.log("setImmediate inside I/O"));
});
```

I/O 콜백 내부에서는 `setImmediate`가 **항상 먼저** 실행된다. I/O 콜백이 처리되는 poll phase 직후가 check phase(setImmediate 실행 단계)이기 때문이다.

### 실험 3: process.nextTick() 우선순위

```javascript
// node event-loop.cjs 로 실행 (순수 Node.js CJS 환경)
console.log("start");

setTimeout(() => console.log("setTimeout"), 0);
setImmediate(() => console.log("setImmediate"));
Promise.resolve().then(() => console.log("promise then"));
process.nextTick(() => console.log("nextTick"));

console.log("end");
```

**결과**: `start` → `end` → `nextTick` → `promise then` → `setTimeout` / `setImmediate`

`process.nextTick()`은 현재 호출 스택이 완료된 직후, 이벤트 루프의 다음 phase로 넘어가기 전에 실행된다.

### 주의: 실행 환경에 따라 결과가 달라진다

같은 코드를 `tsx`로 실행하면 `promise then`이 `nextTick`보다 **먼저** 출력되는 현상이 발생했다. 원인을 추적해보니 두 가지였다.

- **ESM 모듈 시스템**은 코드 실행 전부터 Promise 환경(마이크로태스크 큐) 안에서 동작한다
- **tsx**는 코드 변환 시 비동기 래퍼로 감싸 실행하므로, Promise.then의 우선순위가 달라질 수 있다

순수 `node` 명령어 + CJS로 다시 실행하니 이론대로 `nextTick`이 먼저 실행되었다.

```bash
# tsx — promise then이 먼저 (비동기 래퍼 영향)
pnpm tsx src/playground/event-loop.cjs

# 순수 Node.js — nextTick이 먼저 (이론대로)
node src/playground/event-loop.cjs
```

**교훈**: 이벤트 루프의 실행 순서를 검증할 때는 반드시 **순수 Node.js 환경**(CJS + node 명령어)에서 돌려야 한다. 실행 도구, 모듈 시스템, Node.js 버전에 따라 미묘하게 순서가 바뀔 수 있기 때문이다.

## 마치며

Express 미들웨어 체인과 Node.js 이벤트 루프는 처음에 각각 따로 느껴졌지만, 결국 하나의 흐름으로 연결된다. 요청이 들어오면 이벤트 루프가 이를 감지하고, Express 미들웨어 체인이 순차적으로 처리하며, I/O가 필요하면 다시 이벤트 루프에 위임하는 구조다.

직접 실험하면서 두 가지가 확실히 와닿았다.

- 에러 미들웨어의 인자 4개 규칙은 Express가 `.length`로 구분하기 때문이라는 것
- `process.nextTick`의 우선순위는 **실행 환경에 따라 달라질 수 있다**는 것

다음 글에서는 CJS와 ESM의 모듈 로딩 메커니즘 차이를 더 깊이 파볼 예정이다.
